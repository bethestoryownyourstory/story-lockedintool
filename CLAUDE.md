# STORY - working rules

- **STORY works as one with the phone.** Once on, it is on and always running, like part of the system, and it uses the phone's full potential: STORY does things itself (e.g. silencing apps under the Pages) instead of depending on other apps to cooperate.
- **Black means real black (#000000).** Whenever the owner says "black", use pure #000 -- never a dark grey. The Pages background and cards are #000 (html.focus).
- **No scrollbar lines anywhere in STORY** (no grey/white line down the side of a page). The only exception is the Payments scroll indicator the owner asked for.
- **Pages never zoom in/out on their own.** A page's fitted size is worked out once per screen size (FIT_CACHE) and kept; live changes (prices, profit/loss flips, rows appearing) must not rescale it. Keep layouts the same height in every state (e.g. hidden placeholders).
- **Finish everything, perfectly, before saying it is done.** Every change is complete across every page and state it touches, checked (rendered and tested on all affected pages, Station 3 included), and pushed with a green build. No half-done work, no leftovers for later.
- **The phone's own panel always works on the Pages (owner's call).** The Pages sit in the normal overlay layer under the phone's status bar (clock/battery strip stays visible); never move them above it again, or the notification panel and keyboard break.
- **One thing everywhere.** Anything STORY shows both on the Pages and over apps (Station 3, the dial pad, the message bubble...) is ONE thing: same look, same behaviour, one implementation. Only split it into two when the owner explicitly says so.
- **Unbuilt buttons say so.** Anything not built yet shows STORY's message bubble "... — coming soon" when tapped (COMING_SOON in index.html / showToast). In the app the bubble is drawn natively (StoryNative.toast -> OverlayService.showToast), identical on the Pages, Station 3 and over apps.
- Every STORY window (Pages, Station 3, dial pad, Profile) reloads when the screens update (checkScreens).
- **Profile** opens ONLY from Station 3's profile button and is attached to Station 3 (one piece): its own window (`?s3=1&profile=1`, `profilePane`, built before Station 3's windows so the bar/button/dial pad draw on top), filling the screen around Station 3. A line traces Station 3's bar (top edge + rounded left end); the line is only ever black or white, always the opposite of Profile's background. Profile closes ONLY by tapping Station 3's profile icon again - closing Station 3 leaves Profile open (owner's call), and Station 3's gap (the bar-shaped space inside the line) stays. While Profile is open and Station 3 is closed, the gap scene keeps playing on a loop (owner: as long as there's still the gap) (`storyProfileS3`, told by OverlayService `tellProfileStation3`): two little men walk up, tie a rope to the Station 3 button and try to pull Station 3 out; the boss (angry red mark over his head) storms in and points at them, angry - NO text (owner: "Leave that alone!!" was only the idea) - then leaves, and the two follow. The gap is a REAL gap - see-through AND touches go straight through it to whatever is behind. So Profile is three windows: `profilePane` (`?s3=1&profile=1`, whole screen down to just above the gap's line), `profileGapPane` (`?s3=1&profile=1&gap=1`, bottom-right, bar width + 2dp line by 42dp, never touchable: draws the line, the cut-out background `.pf-bg` (clip-path) and the scene) and `profileStrip` (plain native view in Profile's colour to the gap's left, takes touches). They show/hide together (setShown on profilePane) and follow the bar's width (fitProfileGap); the figures carry a hairline halo so they stay visible on anything. The scene runs at pace SLOW = 1.4 (owner: slowed a bit, "just perfect"). The whole scene (figures, rope, angry mark) happens ONLY inside the gap - nothing ever crosses the line. It never plays when Station 3 is open or when Profile is closed, and the Station 3 button itself never moves (this scene is drawn in Profile's window - the owner's one allowed animation near Station 3). The dial pad and Profile never show together.
  **Messages** (owner): pops up exactly like Profile - the SAME window set (profilePane / profileGapPane / profileStrip), so the same gap, line and scene. Station 3's messages button -> toggleMessages, profile button -> toggleProfile (OverlayService toggleS3Page + s3Page; page side window.storyS3Page shows `.pf-msgs` or `.pf-home`). A page's own button closes the window; the other button switches straight over. Messages are STORY's own end-to-end encrypted messages (not the phone's SMS): sign-up by phone number (text code via Twilio Verify), keys made on the phone and never leaving it, a Cloudflare Worker carries only locked messages; "who can message you" is a privacy setting. Messages screen (owner's drawing): search bar at the top (searches every word in messages you sent or got, plus names; a match shows that message in the row) - nothing beside it (owner removed the new-message pen: never add things the owner didn't ask for); filter boxes Chats / Groups / Archive / Requests (Groups shows two more boxes, Public and Private; Archive = chats you hid - hold a chat for Archive / Unarchive; Requests only shows when the privacy setting `story-privacy`.messages is 'requests'). Rows = profile picture, name (or @username), last message, time, and on the far right how YOUR last message stands: Delivered (they got it, chat not opened) / Seen (opened it and left without typing) / Read (saw it and tapped the keyboard). Live typing indicator: while someone types to you, their row shows "typing" with moving dots (groups: "<name> is typing") in place of the last message; the server calls window.storyMsgTyping(chatId, who) on each keystroke and it clears 6s after the last one. Chats are kept on the phone in localStorage `story-messages` (renderMsgList), which the message server will fill.
  **Create** (Station 3's + button, owner's drawing): the SAME window as Profile / Messages (gap, line, scene), s3Page "create" -> toggleCreate. The real camera is CreateCameraActivity (CameraX, back camera, full screen) running UNDER the window while Create shows (OverlayService.syncCreate starts / finishes it and the Pages step aside); the window is see-through there (`.pf-creating` hides `.pf-bg`). Top right: ✓ post, music under it (coming soon), switch camera (back <-> front) under that (owner asked to switch camera views; placed there - move it if the owner says). Shutter row: + (pick a picture / video from the phone: the same grid as the profile picture, pfGridFor 'create', videos too) on the far left, the shutter in the middle (tap = picture, hold = video; Video box: tap to start / stop, videos only). Boxes: Live (coming soon), Video, Profile, Highlight - none chosen at first; tapping a chosen box again un-chooses it (back to the normal camera); ✓ with no box asks you to choose one. While you look at what you made (or added with +), a delete (bin) button top left throws it away; the shutter does nothing then. The camera steps down (FHD -> HD -> SD -> pictures only -> preview only, switching the missing part in when used) on phones that can't run everything at once; problems show as 'Camera problem: <reason>' and a 6s watchdog says if it never opened. + needs pictures AND videos access (mediaAccess) - an old pictures-only yes makes it ask again. What you made shows full screen before ✓: pictures in the page; videos play on the phone's own player (VideoView in CreateCameraActivity, looping, with sound) under the see-through page - the WebView can't reliably play camera MP4s. Until the camera picture flows, a small status line says which step it's on (opening / starting / waiting for your OK / connecting / Camera problem: reason); it hides on STREAMING. If the camera screen doesn't open within 1.5s, OverlayService retries with a PendingIntent allowed to start from the background (Android 14+). Video covers (highlights) use a still frame saved at ✓ (posts/<id>_t.jpg, story-photo/postthumb/<id>). ✓: Video / Profile -> your profile's posts (`story-posts`, bumpProfileStat('posts', 1)); Highlight -> asks which highlight EVERY time (never the last one by default), with New highlight; max 50 per highlight. Files live in filesDir/posts/<id>.jpg|mp4, served at story-photo/post/<id> (videos with range requests). Highlights (`story-highlights`) show on Profile as circles under the bio (newest item as the cover, the name underneath); opening one is coming soon.
  The circle by NAME is the profile picture (person-outline placeholder until pictures are built); the placeholder name reads "NAME" and @username shows under it. **Profile picture (owner):** tapping the picture only VIEWS it (full-screen circle, tap to close; none yet -> "No profile picture yet"). Everything to do with editing the profile lives in Edit profile (`.pf-editor`), opened by the small pencil button at the top right under the ⋮ (owner moved it there; no big Edit profile button): Change photo is INSTANT (owner: everything in STORY is instant): STORY's own picture grid inside Edit profile (`.pf-photos`, the phone's pictures newest first, thumbnails served straight from the phone at https://appassets.androidplatform.net/story-photo/thumb/<id> by shouldInterceptRequest -> photoResponse). Android asks once for photo access (ProfilePhotoActivity in access mode); Android 14 'selected photos' shows a + More pictures tile; if refused, the phone's own photo picker is used instead (ProfilePhotoActivity; Profile and the Pages step aside for any system screen and come straight back); saved upright, middle square, 1080px, `filesDir/profile_photo.jpg`, loaded from story-photo/profile?v=<time> via StoryNative.getProfilePhoto) and Remove photo; Name, Username and Bio are editable (their own screen `.pf-field` with Save; kept in localStorage `story-profile`, every STORY window updates live; username = 3-30 of a-z 0-9 _ . , no dot at the start/end or two in a row, lowercase; you need a name OR a username or both - never neither (owner). Viewing a profile shows only the values, never label words like "NAME" / "username" (no label with the value under it); only a username -> it takes the name's place. Bio: the word "BIO" shows only while the bio is empty; no uniqueness check until STORY has accounts). Profile's MAIN window lives in the Pages' layer (TYPE_APPLICATION_OVERLAY, under the status bar, added after the Pages) so the keyboard shows above it; it is focusable whenever shown, like the Pages (setShown: flagsFor(false, shown)), and the box asks for the keyboard as it opens / is tapped (StoryNative.setTyping -> profileTyping -> showSoftInput). Bio is editable too (multi-line, 150 max with a counter, line breaks kept on Profile). Profile reopens on its main page (storyProfileReset on close). Profile's numbers are REAL, never made up (owner): stored in localStorage `story-profile-stats` (shared by every STORY window, Profile updates live via the storage event / storyProfileRefresh). Posts = the number of pictures you have posted on your profile (owner) - posting to the profile isn't built yet, so it is 0; Community posts do NOT count. When profile posting is built it calls bumpProfileStat('posts', ...); Following / Followers are 0 until STORY has accounts. fmtCount formats them (1.2k, 100k, 2.5M).
- **System theme (Settings > System theme: Black / White, owner's rule).** Only black and white swap: in White, everything black (or near-black) turns white and everything white (or near-white) turns black - backgrounds, text, numbers, lines, icons, Station 3 (white button + black bar), the dial pad, Profile, the message bubble, the Apps | Pages switch, the setup screen. Any other colour (green, red, gold, blue...) never changes. Web: the swap engine right after `</style>` in index.html (`storySetTheme`, flips style rules, inline styles and SVG colours; originals kept so Black restores exactly). Native: `StoryTheme.kt` (pref "theme", `swap()`), `th()` in OverlayService.kt, `setTheme` re-colours live and tells every window. A note's own colours (paper, cover, ink, their swatches) and the Wallet payment cards keep their own look (KEEP_SEL / KEEP_EL / `data-keep-color`). New black/white colours anywhere in STORY must be plain neutral values so the swap catches them. The AOD screen stays black.
- **Change only what the owner asks for.** Every design in STORY stays exactly as it is unless the owner says to change it - no "improvements", no side changes. If the owner says something is wrong but not where or how it should be, ASK before changing anything. Only fix directly when it's clear what is wrong and how it should look.

- All source files live in the repo root, flat (no folders). `.github/workflows/android.yml` turns them into an Android project at build time; `android.yml` / `screens.yml` / `deploy-worker.yml` in the root are copies of the workflows - keep them identical.
- Fixes to STORY go in these real app files, committed and pushed **straight to `main`**.
- After every push, confirm "Build STORY APK" is green. It fails unless the APK is signed with the repo key (`debug.keystore.b64`, SHA-256 FC58...3569) and its versionCode (run number + 100) is higher than the published one. Only `main` builds are published to phones.
- Updates run for everyone even when STORY is off (WorkManager `UpdateWorker`, every 15 min) and are shown on the setup screen ("Updates: ..."). STORY stays on once started until "Stop STORY" (boot, update, accessibility connect and the worker all restart it).
- **Station 3 is LOCKED (owner's final word).** The corner button sits tight in the bottom-right corner: 40x40, solid pure black #000000 with NO outline (owner: "black that"), rounded top-left, up-left arrow. It never moves, resizes, changes look or animates, open or closed; opening only adds the white bar (40px tall) to its left. No animation anywhere in Station 3 or the dial pad. The dial pad is its own still window (`?s3=1&dial=1`, `dialPane`) in the middle above Station 3, shown/hidden only; Station 3's window is sized once while hidden and never resizes on screen. Never change its position, size or look - and never let another change shift it - unless the owner explicitly asks in their own words. There is ONE Station 3 button: the app's own (bubble in OverlayService.kt), always on screen and on top, open or closed, over apps AND over the Pages (the Pages page draws no Station 3 of its own: `html.native:not(.s3-early) .station3-region` is hidden); tap toggles Station 3. The page never draws a visible button (invisible placeholder only) and the white bar runs on underneath the button (never cut). The bar's white is drawn by the app (barBg in OverlayService.kt, same 40dp maths as the button) so its height matches the button to the pixel; the page draws only the icons on it (html.s3-native-bar). Windows use pinToScreen() so Android can't shift them; the s3-only CSS/JS in index.html and the bubble/pane code in OverlayService.kt hold this in place.
- Always On Display (AodActivity, switch "Always On Display" on the setup screen, off by default): on screen-off a black always-on screen shows at the phone's own brightness (no override - owner's call); Station 3's overlay windows stay on top, unchanged and working. Burn-in protection = a 1-pixel checkerboard over Station 3's windows that swaps every minute (applyAodMask) - Station 3 never moves. Double-tap = lock screen, power = truly off.
- Two channels. Test = `latest` release + gh-pages `/preview/` (the owner's phone, owner mode). Live = `live` release + gh-pages `/` (all users). Both update automatically, no confirmations.
- Using STORY = agreeing to automatic updates (owner's rule, everyone incl. the owner). UpdateActivity is the one-time "Automatic updates - I agree" screen; until agreed STORY stays off (OverlayService/KeepAlive gate on `Release.agreedAuto`). After agreeing, never asked or reminded again. Checks every 20s while the screen is on.
- Nothing goes Live until the owner publishes: the "Publish live update" button (PIN checked by the Cloudflare Worker in `release-worker.js`) or the owner saying "approve" in chat - then run "STORY screens - Test, then Approve". Never put the PIN in the app or the repo.
- The release server address lives in `release.json`. "Deploy STORY release server" puts `release-worker.js` on Cloudflare (needs repo secrets CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID).
